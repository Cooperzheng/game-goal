# Game Goal

把游戏想法或试玩反馈写成制作方能执行、评审能核对的 Goal。只写本次适用的要求；不把参考文档全文复制进 Goal。

## 边界

- 起草与诊断只读；不改项目、不派代理、不启动编排。用户明确要求起草阶段派代理时才例外。
- 先写 Goal 供用户确认，再执行。调用 Skill 不等于授权开发、发布、安装工具或修改配置。
- 用户现有明确约定直接沿用；编排档位须每份 Goal 单独确认，默认上限数字可沿用。宿主权限和停止规则优先。

## 工作流程

1. **复用上下文**：确认目标、反馈原文、范围、保护项与执行宿主。只补会改变方案或可行性的缺口，推测标明；实现参数在相关改动前核实，不为起草提前遍历工程。
2. **写成品标准**：按 [品质与验收](references/quality-bars.md) 写玩家体验、功能与美术目标、参照、通过条件和必要证据。反馈任务写清现象、原因依据、改法与预期；未知原因不装作已确定。
3. **定执行边界**：按 [编排与执行](references/orchestration.md) 选择最小档位，约定预算、停止条件、临时目录和清理范围。授权细节只写一次；独立会话执行的 Goal 要自包含，不能要求执行者另找本 Skill。
4. **交付待确认稿**：目标足以判断即出稿。开头最多 5 条关键确认，覆盖宿主、档位、用量、留存及影响结果的选择；已有约定简写，其余默认决定标明。小任务可压缩成确认块、改法和验收几行。
5. **确认后执行**：短任务直接做；长任务写入项目现有规划位置，用宿主实际支持的方式启动。启动提示引用唯一 Goal、适用授权、完成条件与停止条件，不猜命令。每项结果随执行更新。

检查或精简已有 Goal 时，直接给改稿和实际缺口；保留有价值的具体案例，删空泛形容、重复要求和无关机制。

## Goal 骨架

按任务规模取舍，不逐节凑篇幅：

- **目标与范围**：玩家做什么、为何有趣、完整过程、包含与不做的内容。
- **任务与品质**：每项的改动、好的标准、证据；参照及允许差距，已验证的保护项。
- **执行约定**：宿主与实际档位、职责和额度、整体预算、局部停滞、留存与清理；必要的用户试玩节点。
- **结果**：固定下表，执行中更新，交付时沿用。

| 项 | 反馈编号 | 状态 | 证据（观察、数字或图名） | 差距 |
|---|---|---|---|---|

状态只用“通过／未通过／待你确认／没跑”；没有反馈编号可填 —。表下简列没跑及原因、后续工作、体验入口、回归结果与累计工时。暂停不算完成，不另写重复的结果长文。
