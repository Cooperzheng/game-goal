# Game Goal

Goal 只写执行者自己无从知道的事：用户想要什么成品、已经认可了什么、允许做什么、何时停和何时问。实现和验证方法不写，交给执行者判断。

## 起草

- 起草只读，不派代理；用户确认后才执行。用户已有的约定直接沿用。
- 只补会改变目标、范围或验收的缺口，实现细节不写，不为起草遍历工程。
- 反馈任务逐条写现象、改法和预期，原因不明就写“待查”。多条反馈碰同一系统时合成一项写。
- 开头列需要用户定的事，最多 5 条，没有就不列；交付物固定是其中一条（见下）。其余默认决定标【默认】，确认 Goal 即一并确认。小任务压成几行。交给其他会话执行时，Goal 要自包含。

## 写什么

1. **成品**：玩家做什么、为什么有趣、完整过程；做和不做。参照写到具体图或视频时段、学它什么、允许差多少，不写“AAA”“精美”。反馈任务附原话编号。
2. **每项谁来判**：
   - 硬指标：测试、遥测、脚本能判的（功能、数值、帧时间、缺素材）。没达标就修，到总工时仍没达标就照实报。
   - 用户判：好不好看、手感、压迫感、难度体感，写“待你确认”。不让 AI 评审给观感打分或投票，也不把观感拆成参数去调。
3. **红线**：用户认可过的表现不能变差。改动前留可恢复的版本；变差就修好或撤回，不降标准换通过。要改已认可的表现，先说理由，给出新旧对比。
4. **边界**：文件、分支、端口；不推送、不发布、不碰其他会话。越出文件范围、装全局工具、改宿主配置要再问。授权只对本 Goal 有效。
5. **交付物**：起草时建议、在对话里和用户约定：录屏、截图还是直接试玩，各含哪些场景（如“Boss 二阶段炮雨加安保同时在场”）。执行者只交约定的这些。
6. **何时停、何时问**：大任务先做一个代表样件，能跑就给用户看真实结果，用户点头再铺开；用户拍板的不再复审。只写一个总工时；达标、到上限或卡住就停，带差距和可选路线来问。不追 Goal 没写的指标。

## 少测、少拍

- 过程中靠读状态、遥测和测试判断，截图录屏只为查问题。
- 不做多轮评审和多轮复测。回归只查这次改动碰到的行为，在最终版本跑一次。bot 多局默认不跑，只在结论关乎难度或概率时跑。
- 只清本任务产生的过程文件；用户原件、正式资源、基线和支撑结论的唯一证据不删。

## 记住的坑

- 分数、bot 结果和工具报告成功都不等于好玩好看，工具成功也不能盖过它报的警告。
- 不靠调弱已有效果、堆密内容或降低测试负载刷指标。
- 截图或测试脚本可能改了游戏状态，结果先核对再信；性能在 GPU 空闲时测。
