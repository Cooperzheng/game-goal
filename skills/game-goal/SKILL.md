# Game Goal

这个 Skill 帮用户把要什么讲清楚，不规定 AI 怎么做。Goal 写用户的需求、目标、想看到的东西和关心的点；实现、验证和测试方法都授权给执行者。

判断一句话该不该写进 Goal：执行者不问用户就没法知道的，写；执行者自己能判断好的，不写。

## 起草

- 起草只读，不派代理；用户确认后才执行。用户已有的约定直接沿用。
- 只补会改变目标、范围或验收的缺口，实现细节不写，不为起草遍历工程。
- 反馈任务逐条写现象、想要的变化和预期，原因不明就写“待查”。多条反馈碰同一系统时合成一项写。
- 开头列需要用户定的事，最多 5 条，没有就不列；交付物固定是其中一条。其余默认决定标【默认】，确认 Goal 即一并确认。小任务压成几行。交给其他会话执行时，Goal 要自包含。

## 讲清楚什么

1. **要什么**：玩家做什么、为什么有趣、完整过程；做和不做。参照写到具体图或视频时段、学它什么、允许差多少，不写“AAA”“精美”。反馈任务附原话编号。
2. **关心的点和谁来判**：
   - 硬指标：测试、遥测、脚本能判的（功能、数值、帧时间、缺素材）。到总工时仍没达标就照实报。
   - 用户判：好不好看、手感、压迫感、难度体感，写“待你确认”。AI 不替用户给观感打分或投票，也不把观感拆成参数去调。
3. **想看到什么**：交付物起草时建议、在对话里约定：录屏、截图还是直接试玩，各含哪些场景（如“Boss 二阶段炮雨加安保同时在场”），存到哪里（沿用项目的留档位置，没有就用 `docs/evolution/<Goal 名>/`）。执行者只交约定的这些。
4. **不能动什么**：用户认可过的表现不能变差，也不靠调弱它、堆密内容去刷指标。改动前留可恢复的版本，变差就修好或撤回；要改已认可的表现，先说理由，给出新旧对比。边界写文件、分支、端口；不推送、不发布、不碰其他会话；越出范围、装全局工具、改宿主配置要再问。授权只对本 Goal 有效。
5. **何时停、何时问**：大任务先做一个代表样件，能跑就给用户看真实结果，用户点头再铺开；用户拍板的不再复审。只写一个总工时；达标、到上限或卡住就停，带差距和可选路线来问。不追 Goal 没写的指标。

## 授权给执行者

- 怎么实现、怎么验证、测多少、拍多少，都由执行者判断，够下结论就停。用户的偏好是少测少拍：不做多轮评审和多轮复测，回归只查改动碰到的行为。
- 每轮留档：约定的交付物和结果表引用的关键证据存进留档位置，同一项只留最新有效的一份，被替代的删掉。
- 过程文件（调试截图、录屏、脚本输出）放一个临时目录，每轮交付后清掉，只保留已留档的；只动本任务自己产生的文件。
